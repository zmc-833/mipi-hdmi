### ⚠️ 核实 3：他说"手工改 `.al` 完全无效"—— **需要限定条件**

他实测踩了三次 `.al` 被回写（62 条 → 条目归零 → 63 条），结论是
"必须走 GUI 的 `Source → Add Source...`"。

**但这跟我这边的情况矛盾**：我手工改的 `.al` **是生效的**，66 条里 4 条 track_box 都在，
包括 `CompileOrder 61~64`。

**原因找到了**：

| | 我的 `td_project/` | 他的 `td_project/` |
|:---|:---|:---|
| `settings.cfg` | **无** | 有（TD 生成） |
| `*_Runs/` 目录 | **无** | 有 |
| `.prj` | **无** | 有 |
| 是否用 GUI 打开过 | **从未** | 多次 |

⇒ **真相**：手工改 `.al` **本身是有效的**（TD 打开时会读它）；
**但如果这个工程曾被 GUI 打开过、TD 在内存里维护了工程状态，
手工改的那份就会在下次保存时被回写覆盖**。

**正确的表述应该是**：
- **工程从未用 GUI 开过** ⇒ 手工改 `.al` 有效（我这种情况）
- **工程已在 GUI 里打开过** ⇒ 改 `.al` 无效，**必须走 `Source → Add Source...`**（他这种情况）

他因为是在 GUI 里反复操作，所以踩到了。**他的操作建议是对的，适用范围要加上"GUI 打开过的工程"。**
